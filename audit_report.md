# Отчёт по аудиту проекта vpn-setup

В ходе проведения полного аудита репозитория [vpn-setup](https://github.com/Maksre1/vpn-setup) (компоненты: Python 3.14 + Flask 3.1, SQLite WAL, systemd, Mieru/mita, Hysteria2, fail2ban) были обнаружены критические уязвимости безопасности, серьезные архитектурные ошибки и баги стабильности. 

Ниже представлены все находки, приоритизированные по важности.

---

## 1. Безопасность (Security)

### [КРИТИЧЕСКАЯ] Публичный доступ к списку всех подписок пользователей (Directory Listing)
*   **Где найдено:** `setup.sh` (строки 1083-1098), `cleanup-expired.sh`, `app.py`.
*   **Проблема:** Веб-сервер подписок `vpn-sub.service` запускает встроенный Python-модуль `http.server` на порту `8080` в директории `/var/www/html`:
    ```bash
    ExecStart=/usr/bin/python3 -m http.server 8080
    ```
    Стандартный Python `http.server` при отсутствии файла `index.html` генерирует **Directory Listing** (список файлов в директории). Любой внешний сканер портов или злоумышленник, перейдя по адресу `http://<server_ip>:8080/`, увидит список всех файлов подписок клиентов: `singbox.json`, `clash.yaml`, а также персональные файлы вида `sub-${username}-*.txt`. Злоумышленник сможет скачать эти файлы, декодировать Base64 и получить полные учетные данные для бесплатного доступа к VPN.
*   **Решение:**
    1.  Использовать полноценный легковесный веб-сервер (например, Nginx) с отключенным `autoindex`.
    2.  Или заменить `http.server` на минимальный скрипт Python/Flask/FastAPI, который отдаёт файлы только по точному совпадению имени пути и возвращает `403/404` при обращении к корню `/`.
    3.  Добавить пустой `index.html` в `/var/www/html` как временное решение (но это не защитит от перебора имен файлов, если префиксы простые).

### [ВАЖНАЯ] Отсутствие CSRF-защиты во всей панели управления
*   **Где найдено:** `panel/app.py`, все формы в `panel/templates/`.
*   **Проблема:** В Flask-приложении полностью отсутствует CSRF-защита (Cross-Site Request Forgery). Все POST-запросы (`/login`, `/users/add`, `/users/<id>/edit`, `/users/<id>/delete`, `/users/<id>/reset-password`, `/settings`, `/api/restart`) принимаются без проверки CSRF-токена. Если администратор панели авторизован и случайно перейдет на вредоносный сайт, этот сайт сможет отправить скрытый запрос на удаление пользователей или смену настроек панели от лица администратора.
*   **Решение:** Настроить `flask-wtf` (который устанавливается скриптом, но не импортируется) и использовать `CSRFProtect(app)`, добавив `{{ csrf_token() }}` во все HTML-формы и AJAX-запросы.

### [ВАЖНАЯ] Сброс сессий админа при каждом перезапуске панели (Генерация SECRET_KEY)
*   **Где найдено:** `panel/app.py` (строка 29), `setup.sh` (строка 1984).
*   **Проблема:** Секретный ключ Flask инициализируется следующим образом:
    ```python
    app.secret_key = os.environ.get("PANEL_SECRET", secrets.token_hex(32))
    ```
    Поскольку переменная `PANEL_SECRET` не прописана в systemd-юните `vpn-panel.service`, при каждом перезапуске сервиса Flask (например, при обновлении через `update.sh` или сбое панели) генерируется новый случайный ключ. Это мгновенно аннулирует сессии всех активных администраторов, вынуждая их повторно проходить авторизацию.
*   **Решение:** Генерировать постоянный `PANEL_SECRET` во время работы `setup.sh` и записывать его в `/etc/vpn-setup-state/panel.env`, после чего передавать через `Environment=` в systemd-юнит панели.

### [ВАЖНАЯ] Отсутствие валидации имени пользователя (Инъекция разделителей и RegExp)
*   **Где найдено:** `panel/app.py` (строка 195).
*   **Проблема:** Ввод имени пользователя проверяется только на пустоту (`.strip()`). Отсутствие проверки на допустимые символы приводит к двум угрозам:
    1.  **Инъекция в файлы конфигурации:** Данные пишутся в `vpn-users.conf` в формате `username|password|...`. Если имя содержит символ `|` (например, `user|pass|never`), это полностью нарушит парсинг файла в bash-скриптах.
    2.  **Инъекция в shell-команды:** В `cleanup-expired.sh` используется команда:
        ```bash
        sed -i "s/^${username}|/DISABLED_${username}|/" "$USERS_FILE"
        ```
        Если имя пользователя содержит regex-символы (например, `.*`) или символы слэша `/` (которые используются как разделители в `sed`), скрипт упадёт с синтаксической ошибкой или перезапишет чужие строки конфигурации.
*   **Решение:** Добавить валидацию на стороне Flask: имя пользователя должно состоять только из букв латинского алфавита и цифр (регулярное выражение `^[a-zA-Z0-9_-]+$`), длина ограничена (например, от 3 до 32 символов).

### [ЖЕЛАТЕЛЬНАЯ] Хранение пароля администратора в открытом виде на диске
*   **Где найдено:** `setup.sh` (строка 2008), `panel/app.py` (строка 399).
*   **Проблема:** В целях удобства авто-генерации, пароль администратора сохраняется в открытом виде в файл `/etc/vpn-panel/admin_password.txt`. Хотя на файл установлены права `600`, хранение паролей в открытом виде является плохой практикой (Security through obscurity).
*   **Решение:** Панель должна выводить сгенерированный пароль администратора один раз при установке и не хранить его в открытом виде на диске, используя исключительно хэш в SQLite.

### [ЖЕЛАТЕЛЬНАЯ] Отсутствие ограничений на доступ к файлу БД SQLite
*   **Где найдено:** `panel/models.py` (строки 17-20).
*   **Проблема:** Директория `/etc/vpn-panel` создается, но на сам файл базы данных `panel.db` не накладываются строгие права доступа (600/640). В зависимости от системного `umask` база данных может оказаться доступна для чтения другим локальным непривилегированным пользователям.
*   **Решение:** При инициализации базы данных явно вызывать `os.chmod(DB_PATH, 0o600)`.

## 2. Корректность и стабильность (Correctness & Stability)

### [КРИТИЧЕСКАЯ] Полная неработоспособность мультипользовательского режима (Глобальные ключи)
*   **Где найдено:** `panel/app.py` (строки 180-186), `panel/utils.py` (строки 24-45), `setup.sh` (строки 1843-1855).
*   **Проблема:** 
    1.  **Для Hysteria2:** Конфигурационный файл `/etc/hysteria/config.yaml` содержит только один глобальный пароль `H2_PASS`. В панели при выводе списка пользователей функция `get_hysteria2_uri` считывает глобальный `H2_PASS` из окружения сервера. Таким образом, **все клиенты получают один и тот же пароль Hysteria2**. Разделение пользователей, лимиты трафика и индивидуальная блокировка по истечении срока для Hysteria2 физически не работают.
    2.  **Для Mieru:** Хотя `update_mieru_users()` собирает имена и пароли из SQLite и прописывает их в конфиг Mieru, функция генерации ссылки `get_mieru_uri(config, server_ip)` использует данные глобального администратора (`config.get('MIERU_USER')` и `config['MIERU_PASS']`). Это означает, что **каждый пользователь получает ссылку с логином/паролем администратора**, а его персональные учетные данные игнорируются. Любой заблокированный или удаленный пользователь продолжит работать, так как глобальный аккаунт админа всегда активен.
*   **Решение:**
    1.  Для Hysteria2: Переписать конфигурацию на использование `type: userpass` в `auth` секции (или реализовать HTTP/Command аутентификацию) и динамически обновлять список пользователей.
    2.  Для Mieru: Переписать функцию `get_mieru_uri`, чтобы она принимала конкретные `username` и `password` пользователя из базы данных, а не глобальные из `mieru.env`.

### [КРИТИЧЕСКАЯ] Рассинхронизация и дублирование пользователей при автоочистке (`cleanup-expired.sh`)
*   **Где найдено:** `cleanup-expired.sh`, `panel/models.py` (строка 361).
*   **Проблема:** 
    1.  Скрипт `cleanup-expired.sh` запускается по cron и деактивирует пользователей напрямую в файле `vpn-users.conf` путем добавления префикса `DISABLED_`. При этом **база данных SQLite (`panel.db`) вообще не обновляется**, там пользователи остаются со статусом `is_active = 1`.
    2.  Когда администратор вносит любые изменения через веб-панель (например, редактирует другого пользователя), вызывается `sync_user_to_conf` для синхронизации из SQLite в `vpn-users.conf`. Данная функция ищет пользователя по маске `username|`. Так как в файле строка была переименована в `DISABLED_username|`, поиск завершается неудачей, и функция **записывает пользователя заново в активном статусе**, дублируя его в файле.
    3.  Функция `update_mieru_users` регулярно перезаписывает конфиг Mieru на основе данных SQLite (`SELECT ... WHERE is_active=1`), игнорируя то, что скрипт деактивации сделал в файле.
*   **Решение:** Полностью отказаться от редактирования текстового файла `vpn-users.conf` в bash-скрипте. Логику деактивации истекших пользователей необходимо перенести в Python-скрипт (или запускать Python-скрипт через cron), который будет корректно обновлять базу данных SQLite, вызывать функции `sync_user_to_conf()` и `update_mieru_users()` для применения изменений.

### [ВАЖНАЯ] Бесконечный цикл перезапуска `mita.service` (Mieru) после перезагрузки ОС
*   **Где найдено:** Логи панели (сообщение о частых рестартах).
*   **Проблема:** Mieru (программа `mita`) общается через Unix-сокет, расположенный в папке `/var/run/mita/mita.sock`. По умолчанию в Linux директория `/var/run` монтируется в оперативной памяти (`tmpfs`) и полностью очищается при перезагрузке системы. После перезагрузки сервера папка `/var/run/mita` исчезает. Сервис `mita.service` при попытке запуска не может создать сокет в несуществующей папке и аварийно завершает работу. Из-за настройки автозапуска в systemd (`Restart=always` или `Restart=on-failure`) сервис уходит в циклическую перезагрузку (каждые несколько секунд), нагружая процессор и блокируя подключение клиентов.
*   **Решение:**
    1.  Добавить в systemd-юнит `mita.service` директиву `RuntimeDirectory=mita` и `RuntimeDirectoryMode=0750` с назначением владельца `mita`. Systemd будет автоматически создавать эту папку при старте сервиса и удалять при остановке.
    2.  Или перенаправить сокет Mieru в `/tmp/mita.sock` (для чего изменить конфигурационный параметр `Mita_UDS`).

### [ВАЖНАЯ] Состояние гонки (Race Condition) при редактировании файлов конфигурации
*   **Где найдено:** `panel/models.py` (функции `sync_user_to_conf` и `remove_user_from_conf`).
*   **Проблема:** Запись в текстовый файл `vpn-users.conf` происходит атомарно с точки зрения Python, но не защищена от параллельных запросов. Если два администратора одновременно добавят или удалят пользователя через веб-интерфейс, Flask запустит роуты в параллельных потоках. Оба потока прочитают старое содержимое файла `vpn-users.conf`, внесут свои правки в память и запишут файл обратно. В результате изменения одного из администраторов будут утеряны (Lost Update).
*   **Решение:** Использовать механизм блокировки файлов (например, библиотеку `fcntl` в Python для эксклюзивной блокировки файла конфигурации на время чтения и записи).

### [ЖЕЛАТЕЛЬНАЯ] Отсутствие таймаута при блокировке SQLite
*   **Где найдено:** `panel/models.py` (строка 11).
*   **Проблема:** Подключение к БД: `sqlite3.connect(DB_PATH)`. Без указания параметра `timeout` SQLite использует значение по умолчанию (5 секунд). При высокой конкуренции или во время выполнения долгих операций чтения/записи база данных может вернуть ошибку блокировки (`database is locked`).
*   **Решение:** Увеличить таймаут ожидания блокировки: `sqlite3.connect(DB_PATH, timeout=20.0)`.

### [ЖЕЛАТЕЛЬНАЯ] Отрицательные лимиты трафика и скорости
*   **Где найдено:** `panel/app.py` (строки 204-205, 272-273).
*   **Проблема:** Значения лимитов приводятся к `int()`, но никак не проверяются на знак. Администратор может ввести отрицательные лимиты (например, `-500` ГБ), что вызовет непредсказуемое поведение парсеров трафика.
*   **Решение:** Добавить валидацию `traffic >= 0` и `speed >= 0`.

## 3. Архитектура и код (Architecture & Code)

### [ВАЖНАЯ] Отсутствие файла зависимостей и требований к пакетам
*   **Где найдено:** Корень проекта.
*   **Проблема:** В проекте нет файлов `requirements.txt`, `pyproject.toml` или `Pipfile`. Установка зависимостей в `setup.sh` и `update.sh` выполняется «вслепую» (`pip3 install flask flask-wtf`), без фиксации версий. Это может привести к поломке проекта при выходе мажорных обновлений Flask или Werkzeug в будущем.
*   **Решение:** Создать `requirements.txt` с зафиксированными версиями пакетов (например, `Flask==3.1.0`).

### [ВАЖНАЯ] Отсутствие автоматических тестов
*   **Где найдено:** Корень проекта.
*   **Проблема:** В проекте полностью отсутствуют тесты (unit-тесты, интеграционные). Любое изменение в логике генерации конфигов или авторизации приходится тестировать вручную на «живом» сервере, что повышает риск внесения критических багов.
*   **Решение:** Создать директорию `tests/` и покрыть тестами:
    *   Валидацию пользователей и дат.
    *   Генерацию конфигурационных файлов Mieru/Hysteria2.
    *   Аутентификацию и лимиты попыток входа Flask.

### [ЖЕЛАТЕЛЬНАЯ] Смешение зон ответственности в `models.py`
*   **Где найдено:** `panel/models.py`.
*   **Проблема:** Файл содержит как описание структуры БД SQLite, так и системные операции: перезапуск системных служб (`restart_service`), получение системных характеристик (`get_server_specs`), парсинг трафика сетевых интерфейсов (`get_network_traffic`) и работу с консольными командами. Это нарушает принцип единственной ответственности (Single Responsibility Principle).
*   **Решение:** Вынести все системные вызовы и мониторинг железа из `models.py` в отдельный модуль `panel/system.py` или объединить с `panel/utils.py`.

### [ЖЕЛАТЕЛЬНАЯ] Нереализованные импортированные библиотеки
*   **Где найдено:** `panel/app.py`, `setup.sh`.
*   **Проблема:** Устанавливается пакет `flask-wtf`, но в коде `app.py` он не импортируется и не используется для построения форм и защиты от CSRF. 
*   **Решение:** Либо задействовать `flask-wtf` для форм и CSRF, либо удалить его из списка установки, чтобы не захламлять систему лишними зависимостями.

## 4. Сравнение с референсами (3x-ui & Panel-Naive-Mieru)

### [ВАЖНАЯ] Отсутствие реального ограничения и подсчета трафика по пользователям
*   **Как сделано в 3x-ui:** База данных хранит объем потребленного трафика каждым пользователем. Фоновый демон регулярно опрашивает статистику ядра (Xray-core) и при превышении лимита деактивирует конкретного пользователя.
*   **Как сделано здесь:** Лимиты трафика собираются в панели и записываются в БД, но **система их никак не контролирует**. Пользователь может выкачать терабайты данных при лимите в 5 ГБ, так как нет механизма подсчета трафика на уровне ядра Mieru/Hysteria2 для конкретных клиентов.
*   **Решение:**
    1.  Использовать API/логи Mieru (`mita get connections` или статистику сокетов) и Hysteria2 для периодического подсчета трафика.
    2.  Написать фоновый скрипт на Python (запускаемый по таймеру systemd), который будет суммировать трафик пользователей и переводить статус `is_active` в `0` при превышении лимита.

### [ЖЕЛАТЕЛЬНАЯ] Отсутствие экспорта резервных копий из веб-интерфейса
*   **Как сделано в 3x-ui:** Администратор может в один клик скачать резервную копию базы данных и всех настроек прямо из браузера.
*   **Как сделано здесь:** Бэкапы делаются только локально на сервере в каталоге `/etc/vpn-setup-state/backups` при обновлении системы скриптом `update.sh`.
*   **Решение:** Добавить в веб-панель роут для выгрузки бэкапа базы данных `panel.db` в формате `.zip` или `.tar.gz` для администратора.

## 5. UX/UI (Опыт взаимодействия)

### [ЖЕЛАТЕЛЬНАЯ] Отсутствие индикации загрузки при перезапуске служб
*   **Где найдено:** `panel/templates/dashboard.html` (кнопки перезапуска сервисов).
*   **Проблема:** Операции перезапуска systemd-сервисов (`systemctl restart`) могут занимать до 10-15 секунд. В этот момент интерфейс кажется «зависшим», кнопка никак не меняет своего состояния, что провоцирует администратора на повторные клики.
*   **Решение:** При клике на перезапуск временно блокировать кнопку (`disabled`) и добавлять вращающуюся иконку загрузки (spinner).

### [ЖЕЛАТЕЛЬНАЯ] Недостаточно информативные сообщения об ошибках
*   **Где найдено:** `panel/templates/dashboard.html` (toast-уведомления).
*   **Проблема:** При неудачном перезапуске сервиса выводится стандартное сообщение "Ошибка перезапуска", но детальный вывод (из stderr команды systemctl) не передается админу, что усложняет быструю диагностику без чтения системных логов.
*   **Решение:** Возвращать детальное описание ошибки в JSON ответе `/api/restart` и выводить его в toast-уведомлении.
